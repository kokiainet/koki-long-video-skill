## English

# Long-form tutorials

For software tutorials, methods, and multiple practical use cases. Show the viewer the goal, each step, and the final result, not just a speaker describing features.

## Footage selection & speech

- Index separately recorded clips using file metadata, transcripts, and representative frames. Use available transcripts first and inspect footage as needed instead of watching every retake frame by frame.
- If the user says each file is either useful or not, first mark whole files as selected, alternate, or rejected, with reasons, keeping originals. Copy or reorganize selected files only if file organization was requested.
- Do not infer the official opening from file numbers, creation dates, or transcript starts. Compare camera position, angle, clothes, lighting, continuation, and retakes to find the opening consistent with later footage.
- For multiple deliveries of one idea, choose a complete natural version preserving factual roles. An AI proactively discovering an event after a broad goal is different from a user naming that event and asking AI to find it.
- To replace a sentence, search all footage for a real alternative before changing picture, audio, and captions. If none exists, report the missing recording. Do not invent speech by changing captions or using unrequested synthesis.
- Remove clear repetition, stutters, empty fillers, and excessive gaps; retain necessary causality, steps, conditions, and results.

## Organize by use case

Choose only the parts supported by actual footage:

1. The user's real goal or pain point.
2. Inputs, prompts, or settings supplied to the tool.
3. The process and necessary intermediate results.
4. Final result, limitation, or useful finding.

Explain the learning promise quickly. For several uses, short labels can appear on either side of the speaker as spoken; do not compress a long list into tiny text.

Use clear chapter labels at case changes, anchored to the actual spoken case name. Brief scale/fade entrances are fine while the underlying speaker continues playing. Names, order, and case count come from this video, not a historical project.

## Demonstration screenshots

- Prefer original full-screen screenshots or complete application windows, retaining orientation. Repeatedly enlarging a tiny crop causes blur and loss of context.
- For emphasis, use high-resolution source, a detail zoom, or a highlight with enough surrounding UI to show the path. Replace low-resolution material or report the gap; magnification is not more source detail.
- Let screenshots lead concrete steps. Place the speaker to the side or in a lower-right inset, giving the UI enough area. Keep inset, captions, and step text clear of key buttons, fields, and results.
- Check menus, buttons, and key text at normal playback size, not only editor zoom. Reveal tall screenshots progressively with the actual operation.
- Preserve proportions. Crop irrelevant system bars and clutter without losing application title, entry points, or key information.
- Match images semantically: show the named platform or calendar when discussed. Use separate assets for different platforms, not the same screenshot across the entire passage.
- Use short current-step/action/result instructions near the screenshot, generally one main action per screen. Explanations should not be smaller than the UI or block controls.

## Closing & factual completeness

Promotions, referral codes, and expiry dates must come from confirmed user information. Display them clearly without inventing benefits, discounts, or deadlines.

Show supplied identity assets with the corresponding self-introduction. Match each publication/photo to the actual claim rather than piling all identity images together.

Build a case–step–asset coverage table. Check every case, especially the last case and closing, for screenshots seconds early/late, missing website/calendar, overly long reuse, or unreadable key text.

For navigation/captions see [Finishing](finishing.md); for covers, titles, show notes, and case timestamps see [Publishing](publishing.md). After speech changes use [Timeline synchronization](timeline-sync.md).

## 简体中文

# 教程类长视频

适用于软件教程、方法分享、多个 case 的实操视频。视频应让观众知道“我要完成什么、每一步怎么做、最后得到什么”，而不只是看着人物听功能介绍。

## 素材筛选与口播

- 对分段录制的原片，先用文件信息、转写和少量代表帧建立索引，避免逐帧看完所有重录。优先利用当前可用的转写结果，按需查看原始画面。
- 用户说明“一个文件要么有用要么没用”时，先按整文件标为使用、备用或废弃；记录理由，保留原件。只有用户要求文件整理时，才将选用文件复制或归入新的子文件夹。
- 不按文件序号、创建时间或转写开头推断哪段是正式第一条。对比机位、角度、服装、光线、接续句及重录关系，找到与后续素材一致的开场。
- 一项意思有多个版本时，选完整、自然、符合用户要表达事实的一版。特别检查任务主体：例如“让 AI 帮我进入某个生态，AI 主动找到了活动”不能剪成“我点名要求 AI 找该活动”。
- 用户要替换某句时，先搜索所有原片中的真实替代版本，再更换音视频和字幕。没有对应录音，就说明缺失；不通过字幕改写或未经请求的合成，让人物说出原本没说的话。
- 只清理明确重复、口吃、无意义口气和过长空白；保留必要的因果、步骤、条件和结果。

## 按 case 组织

每个案例按实际内容选用以下骨架，不为形式补造步骤：

1. 用户的真实目标或痛点。
2. 给工具的输入、提示词或设置。
3. 操作过程和必要的中间结果。
4. 最终结果、限制或值得注意的发现。

开头快速说明能学到什么。枚举多个用途时，可以在人物两侧分列短文字，随口播逐项出现；不把一长串例子缩成一块难读的小字。

案例切换时用清晰章节词建立识别；例如说到案例名称的那个词时出现大标题。可以短促放大或淡入，保持下面的人物视频正常播放。章节与案例数量来自本期内容，不固定沿用旧项目的名称、顺序或数量。

## 操作截图：先看清，再追求装饰

- 优先使用用户原始电脑截图或完整应用窗口，保留帮助观众定位的上下文。不要把原图很小的一块反复放大，造成模糊、失去方位。
- 确需局部强调时，用原始高分辨率图片、局部放大或高亮，保留能认出操作路径的范围。尺寸不足就换清楚的源图或报告缺失，不用放大倍数掩盖低清晰度。
- 具体步骤以截图为主：把人物移到一侧或缩成右下角小窗，给应用界面足够面积。小窗、字幕和步骤文字都避开关键按钮、输入框及结果。
- 检查普通播放尺寸下菜单、按钮和重要文字是否能辨认，不以编辑器放大后的清晰度作为依据。长截图可按实际操作逐步展示，不一次塞满。
- 画面比例保持自然。裁掉与教程无关的系统栏或杂乱边缘时，不误裁应用标题、操作入口和关键内容。
- 按语义切图：说到平台就用该平台，说到网站日历就显示对应日历界面。几个不同平台依次出现时，使用各自素材，避免整段重复同一张图。
- 操作说明使用“当前步骤／动作／结果”的短句，贴近相关截图。一般每屏解释一个主要动作，避免解释文字比原界面还小或挡住操作区域。

## 收尾与事实完整性

优惠、邀请码、有效期等来自用户确认的信息，用醒目的主视觉文字框呈现；不自行编造收益、折扣或时限。

自我介绍时放与该句身份相关的用户素材。不同刊物、报道和个人照片按实际叙述匹配，不把所有身份图默认堆上去。

验收时建立“案例—步骤—素材”覆盖表：每个案例都有对应画面，最后一个案例和收尾也检查；重点排查截图早到／晚到几秒、漏放个人网站或日历界面、同一张图覆盖太长、关键文字模糊。

需要章节导航和字幕时，读取 [视听与交付](finishing.md)；需要教程封面、正式标题、shownote 和案例时间轴时，读取 [封面与发布素材](publishing.md)。后续口播改变时读取 [时间线同步](timeline-sync.md)。
